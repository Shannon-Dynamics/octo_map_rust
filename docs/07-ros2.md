# ROS 2 Integration

Two pieces, and the split between them is the design:

| | What it is | Depends on ROS |
|---|---|---|
| `crates/octomap-ros` | The conversions: `PointCloud2` in, `octomap_msgs/Octomap` out | **No** |
| `ros2/octomap_server_rs` | A mapping node built on them, using `r2r` | Yes |

`octomap-ros` takes the plain data a message carries — a byte blob, a list of
field descriptors, a resolution — never a generated message type. So it builds
and tests on a machine with no ROS installed, its logic is covered by ordinary
unit tests, and which client library you use stays your choice. Everything that
needs a middleware lives in the node, and the node is thin.

If you want the octree in your own node, depend on `octomap-ros` and skip
`octomap_server_rs` entirely. If you want a working `octomap_server`
replacement, build the node.

---

## 1. Prerequisites

ROS 2 (developed against **Jazzy**), Rust, and the toolchain `r2r` needs to
generate its bindings:

```bash
sudo apt install -y clang libclang-dev python3-pip

sudo apt install -y ros-$ROS_DISTRO-octomap-msgs   # the message package
sudo apt install -y ros-$ROS_DISTRO-octomap        # only for scripts/ros2/, see §7
```

Rust itself: install it however you normally would. The upstream instructions
are at <https://rustup.rs>; this document does not reproduce a
pipe-to-shell command.

`octomap_msgs` is required — the node publishes its message type. The C++
`octomap` package is **not** needed to run anything here; it is used only by the
interoperability test, which decodes the node's output with the reference
library on purpose.

Verify the messages are installed and, importantly, that they load:

```bash
source /opt/ros/$ROS_DISTRO/setup.bash
ros2 interface show octomap_msgs/msg/Octomap
ros2 topic pub -1 /probe octomap_msgs/msg/Octomap "{binary: true, id: OcTree}"
```

The second command matters more than the first. `ros2 interface show` only
reads a file; publishing loads the typesupport libraries, which is where a
mismatched `octomap_msgs` build fails. See §8.

## 2. Building

### With cargo, for development

```bash
source /opt/ros/$ROS_DISTRO/setup.bash
cd ros2/octomap_server_rs
cargo build --release
./target/release/octomap_server_rs --ros-args -p resolution:=0.05
```

ROS **must** be sourced before `cargo build`: `r2r` reads
`AMENT_PREFIX_PATH` in its build script and generates Rust bindings for every
message package it finds there. Building without it produces a binary that is
missing the message types, and adding a package later needs
`cargo clean -p r2r_msg_gen` to pick it up.

Under WSL, point cargo at a Linux path. Building on `/mnt/d` works but the 9p
filesystem makes linking take minutes:

```bash
export CARGO_TARGET_DIR=$HOME/.cache/octomap_server_rs_target
```

### With colcon, for deployment

The package is a normal `ament_cmake` package that shells out to cargo, so it
drops into a workspace like anything else:

```bash
ln -s /path/to/octoMap-rust/ros2/octomap_server_rs ~/ros2_ws/src/
cd ~/ros2_ws && colcon build --packages-select octomap_server_rs
source install/setup.bash
ros2 run octomap_server_rs octomap_server_rs
```

The symlink is deliberate: the package's `Cargo.toml` has path dependencies on
`../../crates/`, so it has to keep seeing the repository around it.

## 3. Running

```bash
ros2 launch octomap_server_rs octomap_server.launch.py \
    cloud_in:=/camera/depth/points \
    frame_id:=map \
    resolution:=0.05 \
    rviz:=true
```

or, without a launch file:

```bash
ros2 run octomap_server_rs octomap_server_rs --ros-args \
    -r cloud_in:=/camera/depth/points \
    -p resolution:=0.05 -p frame_id:=map
```

Note the difference: `cloud_in` is a **topic remap** (`-r`), not a parameter.
The node always subscribes to a topic called `cloud_in` and you point that at
the real one.

## 4. Interface

### Subscribes

| Topic | Type | Notes |
|---|---|---|
| `cloud_in` | `sensor_msgs/PointCloud2` | Best-effort by default; remap this |
| `/tf`, `/tf_static` | `tf2_msgs/TFMessage` | Only when `use_tf` is true |

### Publishes

| Topic | Type | Notes |
|---|---|---|
| `octomap_binary` | `octomap_msgs/Octomap` | One bit per voxel. What RViz's octomap display and most consumers read |
| `octomap_full` | `octomap_msgs/Octomap` | Full log-odds, so a receiver can keep updating it. Several times larger |
| `occupied_cells_vis_array` | `visualization_msgs/MarkerArray` | Cubes, colored by height. Needs no extra RViz plugin |
| `free_cells_vis_array` | `visualization_msgs/MarkerArray` | Off by default; there are far more free cells than occupied ones |
| `octomap_point_cloud_centers` | `sensor_msgs/PointCloud2` | Occupied cell centers |

All of them are latched (`transient_local`) unless `latch` is false, so RViz
started a minute late still gets the current map.

### Services

| Service | Type | Effect |
|---|---|---|
| `octomap_binary` | `octomap_msgs/GetOctomap` | Returns the binary map |
| `octomap_full` | `octomap_msgs/GetOctomap` | Returns the full map |
| `~/reset` | `std_srvs/Empty` | Empties the map and clears the markers |

```bash
ros2 service call /octomap_server/reset std_srvs/srv/Empty
```

## 5. Parameters

Read once at startup. Changing one afterwards with `ros2 param set` updates
what `ros2 param get` reports but does **not** reconfigure the running node —
the map is already built to the old resolution and sensor model, and switching
either mid-run would corrupt it. Restart instead.

### Map

| Parameter | Default | Meaning |
|---|---|---|
| `resolution` | `0.1` | Smallest voxel edge length, in meters |
| `frame_id` | `map` | Frame the map is built and published in |
| `compress_map` | `true` | Prune the tree after every scan |

### Frames

| Parameter | Default | Meaning |
|---|---|---|
| `use_tf` | `true` | Resolve the cloud's frame into `frame_id` through `/tf` |
| `sensor_frame_id` | `""` | Override the cloud's own `header.frame_id` |
| `sensor_transform` | `[]` | `[x, y, z, roll, pitch, yaw]`, used when `use_tf` is false |

`sensor_transform` is what makes `use_tf: false` usable for a fixed sensor
mounted at a height. Without it every ray is traced from the map origin, and
the free space below the sensor comes out wrong.

### Filtering

| Parameter | Default | Meaning |
|---|---|---|
| `max_range` | `-1.0` | Longest ray integrated; negative is unlimited |
| `min_range` | `0.0` | Drop returns closer than this — the robot's own chassis |
| `min_z` / `max_z` | unbounded | Height limits, applied **after** the transform |
| `point_stride` | `1` | Keep one point in every N |
| `discretize` | `true` | Collapse duplicate endpoints to one ray per voxel |

`max_range` and `min_range` are not symmetric, on purpose. A point past
`max_range` still clears the space along its ray out to that distance; a point
inside `min_range` is discarded outright. Capping a ray and deleting a
measurement are different operations, and conflating them leaves unknown voids
where the sensor plainly saw through.

`point_stride` is the first knob to reach for when insertion cannot keep up —
see §6.

### Sensor model

| Parameter | Default | Meaning |
|---|---|---|
| `prob_hit` | `0.7` | Probability assigned to a hit |
| `prob_miss` | `0.4` | Probability assigned to a miss |
| `occupancy_thres` | `0.5` | At or above this, a voxel counts as occupied |
| `clamping_thres_min` | `0.12` | Lower clamp |
| `clamping_thres_max` | `0.97` | Upper clamp |

These are the reference `OcTree` defaults. Clamping is what lets the map forget:
without an upper clamp a voxel seen occupied a thousand times can never be
cleared.

### Output

| Parameter | Default | Meaning |
|---|---|---|
| `publish_period` | `1.0` | Seconds between publishes |
| `publish_full_map` | `true` | Also publish `octomap_full` |
| `publish_markers` | `true` | Publish occupied-cell cubes |
| `publish_free_markers` | `false` | Publish free-cell cubes too |
| `publish_centers` | `true` | Publish cell centers as a cloud |
| `color_factor` | `0.8` | Compression of the height-color spectrum |
| `latch` | `true` | Publish with `transient_local` durability |
| `best_effort_cloud_qos` | `true` | Subscribe to `cloud_in` best-effort |

Publishing is on a timer, decoupled from the scan rate: serializing a large map
at 30 Hz would cost more than building it.

## 6. Sizing the workload

Insertion is single-threaded, and a full-resolution depth camera produces more
points per frame than any single-threaded occupancy mapper will absorb at a fine
resolution — the C++ `octomap_server` included. Configuring the workload is
therefore part of deploying the node rather than an optimization step.

The node does not silently drop scans to keep up. It integrates inline, and the
best-effort subscription lets the middleware discard what does not fit, which
is the right failure mode for a sensor but means an unconfigured node maps at a
fraction of the frame rate. Four knobs, cheapest first:

1. **`point_stride`** — the direct one. `4` quarters the work and costs almost
   nothing where the map is sparse.
2. **`max_range`** — ray length dominates the cost. Capping at 5 m on a sensor
   that reports 30 m is usually a large win and no loss.
3. **`resolution`** — halving it is an eightfold change in node count.
4. **`publish_period`** — if the map is large, serialization is not free.

The C++ `octomap_server` parallelizes insertion with OpenMP and this port has no
equivalent. That is a known limitation, listed in
[`../ROADMAP.md`](../ROADMAP.md).

## 7. Testing without a sensor

`scripts/ros2/` has an end-to-end check that needs no hardware:

```bash
source /opt/ros/$ROS_DISTRO/setup.bash
./scripts/ros2/smoke_test.sh
```

It publishes a synthetic wall as a `PointCloud2` (with NaN points mixed in, as a
depth camera produces), relates the sensor frame to the map with a static
transform, runs the node, captures `/octomap_binary`, and then decodes the
payload **with the C++ OctoMap library** and queries it.

That last step is the point. A Rust round trip would only show the port is
self-consistent; having the reference implementation read the bytes off the wire
and agree about which voxels are occupied, free and unknown is what shows the
two are speaking the same format.

The pieces are usable separately:

```bash
python3 scripts/ros2/fake_cloud_publisher.py --topic /cloud_in --frame sensor
python3 scripts/ros2/capture_octomap.py --topic /octomap_binary --out /tmp/map.payload
g++ -O2 -o /tmp/decode scripts/ros2/decode_octomap_payload.cpp -loctomap -loctomath
/tmp/decode /tmp/map.payload 0.1 binary  3.02 0.02 0.52 occupied
```

## 8. Troubleshooting

**`undefined symbol: _ZN8eprosima7fastcdr3Cdr9serializeEPc`** on the first
publish. The installed `octomap_msgs` was built against Fast-CDR 1.x while
Jazzy ships Fast-CDR 2.x, so its Fast-RTPS typesupport cannot resolve its own
dependencies. Nothing in this repository can work around it: the message
package is broken for C++ and Python too.

Note *when* it fires. The typesupport is loaded lazily, so creating a publisher
succeeds and only the first serialization fails — which means
`ros2 topic pub -1 …` appears to work while it waits for a subscriber, and
`ros2 interface show` never touches the library at all. Neither is a test.
This is:

```bash
python3 -c 'import rclpy; from octomap_msgs.msg import Octomap
rclpy.init(); n = rclpy.create_node("probe")
n.create_publisher(Octomap, "/probe", 1).publish(Octomap(id="OcTree"))
print("ok")'
```

Confirm it with `nm`, which needs nothing running:

```bash
nm -D -u $(ros2 pkg prefix octomap_msgs)/lib/liboctomap_msgs__rosidl_typesupport_fastrtps_c.so \
  | grep fastcdr3Cdr9serializeEPc      # any output means the broken build
```

The clean fix is the distribution's own package:

```bash
sudo apt install --reinstall ros-$ROS_DISTRO-octomap-msgs
```

If that is not an option — the copy in `/opt/ros/$ROS_DISTRO` is often not an
apt package at all, so `dpkg -l ros-$ROS_DISTRO-octomap-msgs` comes back
empty — rebuild it into an overlay, which needs no root and shadows the broken
one:

```bash
mkdir -p ~/octomap_msgs_ws/src && cd ~/octomap_msgs_ws/src
git clone --depth 1 --branch ros2 https://github.com/OctoMap/octomap_msgs.git
cd .. && colcon build --allow-overriding octomap_msgs
echo 'source ~/octomap_msgs_ws/install/setup.bash' >> ~/.bashrc
```

`--allow-overriding` is required and colcon will say so: overriding a package
from an underlay is exactly the intent here.

As an immediate workaround, `RMW_IMPLEMENTATION=rmw_cyclonedds_cpp` avoids the
Fast-RTPS typesupport entirely and needs nothing rebuilt.

**`dropping scan: frame "camera_link" has not appeared on /tf`.** Expected for
the first second or two while TF fills in. If it persists, check
`ros2 run tf2_tools view_frames` — the log line reports how many transforms the
node knows, which separates "TF is silent" from "TF is up but the chain to the
sensor is missing".

**`no usable points in a cloud of N`.** The counts in the message say which
filter took them. All non-finite on an organized depth cloud usually means the
sensor genuinely returned nothing; all outside the height range means `min_z` /
`max_z` are set for a different frame — remember they apply **after** the
transform, in the map frame.

**The map appears but RViz draws nothing.** Check the fixed frame matches
`frame_id`, and that the marker display's QoS durability is set to Transient
Local — a Volatile subscriber sees nothing until the next publish.

**Scans smear along the robot's path.** The transform buffer keeps only the
latest transform per edge and does not interpolate to the cloud's timestamp. On
a fast robot, or a bag replayed with clumped stamps, that error is visible. It
is a real limitation of not binding to `tf2`; see the module docs in
`ros2/octomap_server_rs/src/tf.rs`.

## 9. Using the conversions directly

```toml
[dependencies]
octomap-core = { path = "…/crates/octomap-core" }
octomap-ros  = { path = "…/crates/octomap-ros" }
```

```rust
use octomap_core::{OcTree, Point3};
use octomap_ros::pointcloud2::{Cloud, FieldRef};
use octomap_ros::{msg, ScanFilter, Transform3};

// Whatever your client library calls a PointCloud2.
let fields: Vec<FieldRef> = message.fields.iter()
    .map(|f| FieldRef::new(&f.name, f.offset, f.datatype, f.count))
    .collect();
let cloud = Cloud::new(
    &fields, &message.data, message.width, message.height,
    message.point_step, message.row_step, message.is_bigendian,
)?;

let sensor_in_map = Transform3::from_translation(1.0, 0.0, 0.5);
let scan = ScanFilter { min_range: 0.3, ..Default::default() }
    .apply(&cloud, &sensor_in_map);

let mut map = OcTree::new(0.1)?;
map.insert_point_cloud(&scan, sensor_in_map.origin(), 10.0, false, true);

// Straight into an octomap_msgs/Octomap.
let payload = msg::binary_payload(&map)?;
// payload.binary, payload.id, payload.resolution, payload.into_i8()
```

### The one thing to get right

The `data` field of an `octomap_msgs/Octomap` is **not** a `.bt` or `.ot` file.
The message carries the resolution and tree id in their own fields, so the
payload is headerless — the node bytes only. Putting a whole file in there
produces a message that no consumer can decode, and it is the most common way
to get this wrong.

`msg::binary_payload` / `msg::full_payload` produce the right thing, and
`msg::decode` reads it. `octomap_core::io::write_binary` and friends produce
files; the `*_data` variants produce payloads.
